# connectrpc/rust

Port of protoc-gen-connect-rust, the protoc plugin of
[connect-rust](https://github.com/connectrpc/connect-rust) (ConnectRPC service traits, typed
clients and monomorphic dispatchers for Rust, over buffa message types), as published on
[buf.build/connectrpc/rust](https://buf.build/connectrpc/rust).

- Upstream: <https://github.com/connectrpc/connect-rust/tree/v0.9.0> (`connectrpc-codegen`:
  `src/bin/protoc-gen-connect-rust.rs`, `src/codegen.rs`, `src/comments.rs`), Apache-2.0,
  Copyright The Connect Authors.
- The remote plugin is `cargo install connectrpc-codegen --version 0.9.0 --locked` built with
  Rust 1.98.0 (buf's Dockerfile). Locked versions that show in the output: buffa-codegen 0.9.1
  (buffa and buffa-descriptor 0.9.1), prettyplease 0.2.37, syn 2.0.119, quote 1.0.47,
  proc-macro2 1.0.107, heck 0.5.0.

## Usage

```yaml
plugins:
  - local: protoc-gen-uni
    out: gen/connect
    opt: [uni-name=connectrpc/rust, uni-version=v0.9.0, buffa_module=crate::proto]
```

Message types come from a separate `anthropics/buffa` run (views enabled); `buffa_module` (or
`extern_path=.=<path>`) says where that module tree is mounted.

## Class

Formatted: each `<stem>.__connect.rs` is a `quote!` token stream parsed with syn and printed with
prettyplease (`format_token_stream`), without a header. The port builds the syn nodes directly for
the prettyplease port (`pkg/languages/rust/formatters/prettyplease`). The stitchers
(`<pkg>.mod.rs`, or `<pkg>.rs` under `file_per_package`) are plain text with the header
`// @generated by connectrpc-codegen. DO NOT EDIT.`.

## Layout

- `v0.9.0/generator.c`: `protoc-gen-connect-rust.rs` (decode_request, then generate; errors are
  anyhow's `Error: <message>` of the failing process, returned as `CodeGeneratorResponse.error`).
- `v0.9.0/codegen.c`: `codegen.rs` (`generate` with the option parsing and its error texts,
  `generate_services`, the service, client, dispatcher, spec constant, owned-view alias and
  `Encodable` impl code). The unified `generate_files` path (buffa types and stubs in one tree) is
  library API that the plugin never takes and is not ported.
- `v0.9.0/comments.c`: `comments.rs` (rustdoc sanitizer of service and method comments).
- `pkg/languages/rust/buffa-codegen`: the parts of buffa-codegen the plugin uses
  (`CodeGenContext::for_generate`, `rust_type_relative(_split)`, `make_field_ident`,
  `rust_path_to_tokens`, file names, `FeatureGateNames::is_valid_name`, `decode_request` with the
  element-memory budget). They are identical in 0.9.1 and 0.9.2 (diffed), so the library's 0.9.2
  code serves both; nothing is versioned.

## Golden tests

`testdata/checksums/connectrpc/rust/v0.9.0.buf.gen.yaml`: every input with nine groups:
`module` (`buffa_module=crate::proto`), `file-per-package`, `gate` (`extern_path=.=crate::pb`,
`gate_client_feature=client`, `encodable_impls=all_messages`), `extern` (WKT `extern_path`,
`no_json`, `no_register_fn`, `strict_utf8_mapping`), `gate-default` (`gate_client_feature`
without a name, `encodable_impls=outputs`, `element_memory_limit=unlimited`), `no-module` (no
options: "not covered by any extern_path mapping" on inputs with services), and the errors
`error-memory` (`element_memory_limit=1024`), `error-encodable` and `error-unknown`.
`services-case` fails with the method-name collision error.

## Options

All options of `generate` are parsed with upstream's error texts: `buffa_module=`,
`extern_path=<proto>=<rust>` (repeatable, longest prefix wins), `gate_client_feature[=<name>]`
(the name is checked as a Cargo feature name), `encodable_impls=all_messages|outputs`,
`element_memory_limit=<bytes>|unlimited|max`, `file_per_package`, and `strict_utf8_mapping`,
`no_json`, `no_register_fn` (accepted, no effect on service stubs, as upstream).

`element_memory_limit` sets the budget of the request decode exactly like buffa: every element of
a repeated message, string or bytes field of the decoded descriptors costs `size_of` of its Rust
type (`bc_decode_request`; checked against the remote plugin at the exact threshold on four
inputs). The remote plugin reads `BUFFA_ELEMENT_MEMORY_LIMIT` from an environment it does not set,
so the port does not read it either: without the option the budget is 1 GiB.

## Unsupported

Every option the plugin accepts is ported. Non-ASCII identifier characters in a Rust path (an
`extern_path`/`buffa_module` target, a package or type name) fail with "unsupported by
protoc-gen-uni: non-ASCII identifier character in Rust path ..." instead of the Unicode XID check
of proc-macro2.

## Known differences

- Request decoding: pkg/pb parses the request; buffa's decode errors other than the element-memory
  budget (invalid UTF-8 in strings, a wire type that does not match the descriptor field, its
  recursion and unknown-field limits) are not reproduced.
- Rust panics are errors instead: an `extern_path`/`buffa_module` target with a segment that is not
  an identifier (`crate::`, `my-crate`, a written raw identifier `crate::r#foo`; proc-macro2
  `Ident::new` panics) gives "Unsupported: Rust path ..."; a view type whose module is not absolute
  (an `extern_path` that maps a package to plain `crate`), which upstream unwraps in the route
  registration after its alias was suppressed, gives the "not covered by any extern_path mapping"
  error.
- Deep method chains: prettyplease prints the receiver chain of the Ext trait router recursively,
  one level per method, so upstream's stack bounds the method count (not measured); the port
  prints the chain in a loop and generates it.
